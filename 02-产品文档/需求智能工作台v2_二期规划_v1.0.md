# 需求智能工作台 v2 · 二期规划（v1.0）

> 日期：2026-10-27　状态：规划待评审（编码开工需另行发话）
> 上游依据：《产品需求文档_最终版》（定位与红线）、《技术文档_最终版》§5（投产验收结论）、《项目进度与交付记录_最终版》（当前进度）。
> 本规划回答一个问题：**怎么让这个产品从「功能做完」走到「价值被验证」。**

---

## 0. 出发点：当前的核心矛盾

产品完成度 ≠ 产品价值验证。

| 事实 | 含义 |
|---|---|
| 功能已全部实现并超交（25 接口 / 6 视图 / 28 项测试 / P0 与 P1-1 审计已修） | 「系统该是什么样」已做完 |
| 未投产、零真实用户 | 背景的成功标准「团队能更快说清楚需求」**无法验证** |
| P1（审计日志、生产部署形态）未补 | 不具备真实团队使用的工程条件 |
| 规则引擎语义能力弱（相关性/背书靠 2-gram 词重合） | 体验有明确增强空间，但不能动判断层 |

按「有变现价值 + 较好交互体验 + 有真实使用用户」的价值观，当前最缺的是**真实使用用户**。

**规划主线：先试点拿真实用户（Phase 1）→ 再用 LLM 增强体验（Phase 2）→ 最后数据闭环证明价值（Phase 3）。** 三期各自可独立验收，顺序不可调换（Phase 2 依赖 Phase 1 的审计日志，Phase 3 依赖试点的真实数据）。

---

## Phase 1 · 试点上线（目标：拿到真实用户）

### 范围

| 项 | 内容 |
|---|---|
| P1-1 审计日志 | 审计表（操作者/动作/对象/前后值/时间），关键写操作落审计：登录、改密、账号增删改、基座编辑、需求创建/评审/导出、公开提需。**这也是 Phase 2 LLM 调用留痕的硬前置** |
| P1-2 生产部署形态 | 去 `--reload`、Nginx 反代 + HTTPS、进程守护（systemd 或等价物）、前端 dist 静态托管、Cookie 加 `secure` |
| 试点动作 | 选 1 个真实团队；导入真实项目基座（公司业务/背景/进度填真数据）；把项目提需入口（链接+二维码）发到真实渠道 |

### 成功标准可测化（对齐北极星指标）

| 指标 | 口径 | 试点期目标 |
|---|---|---|
| 从提交到首次可评审的中位时长 | 需求创建 → 进入「待评审」的时间 | 先定基线，不设门槛 |
| 已入池需求关键判断可追溯率 | 已入池需求中有证据或反证支撑的比例 | 先定基线 |
| 活跃使用 | 周活跃提交人 / 评审人 | ≥3 人/周 |

### 出口标准

真实团队连续使用 2–4 周，产生 ≥20 条真实需求记录，且上述三项指标有基线数据。

### 明确不做

多租户隔离、权限粒度细化、通知渠道接入、移动端适配增强。

## Phase 2 · LLM 增强层（目标：体验跃升，红线不动）

### 架构原则：分层

- **判断层不动**：规则引擎（`analysis.py`）仍是真实性/相关性/优先级的唯一结论来源，结论可复现、可追责。
- **增强层加 LLM**：只产出「建议」，UI 一律标注「AI 建议」，与规则结论视觉隔离。

### 四个增强点（按价值排序）

| # | 增强点 | 解决的实测短板 | 风险 |
|---|---|---|---|
| 1 | 基座背书语义匹配 | 2-gram 词面匹配漏判语义相同表述（「拼日报」vs「汇总报表」） | 低（只影响展示与兜底判定提示） |
| 2 | 追问建议生成 | 模板化提示不针对原话，PM 仍要想问题 | 中（生成内容需人采纳才落库） |
| 3 | 公开提需原话自动结构化 | 员工写不出「场景/问题/影响」结构 | 中（员工确认后才提交） |
| 4 | 需求卡润色 | 字段拼接可读性一般 | 低 |

### 工程护栏（硬要求）

1. 环境变量开关（如 `WORKBENCH_LM_API_KEY`）：不配置时完全走现状规则引擎，**零回归**。
2. 每次 LLM 调用落审计：输入摘要/输出/耗时/token 用量（依赖 Phase 1 的审计表）。
3. LLM 路径的测试只断言结构不断言内容；密钥不入库不入仓。
4. 新交互（详情抽屉 AI 建议区、提需表单结构化预览）**先出线框/设计稿评审，再实现**。

### 明确不做

LLM 参与真实性/优先级结论、自动状态流转、任何形式的 agent 自主决策、多轮对话机器人。

### 出口标准

四个增强点上线后，试点团队 PM 对「追问质量」「背书命中率」的主观评分提升，且判断层结论零变更（回归测试全过）。

## Phase 3 · 数据闭环（目标：证明价值）

| 项 | 内容 |
|---|---|
| 判断准确率回看 | 已入池需求的事后命中率（入池后实际投产/产生效果的比例），校验规则引擎阈值 |
| 使用统计看板 | 收口 P2 看板项：提交量、评审周期、状态分布趋势 |
| 试点复盘报告 | 用真实数据回答背景的成功标准：团队是否更快说清楚需求的场景、证据、相关性和取舍 |

**出口标准**：复盘报告给出明确结论——推广到更多团队 / 继续打磨 / 终止。

---

## 风险与依赖

| 风险 | 影响 | 缓解 |
|---|---|---|
| 试点依赖真实团队配合（体外依赖） | Phase 1 出口标准无法达成 | 提前锁定团队与对接人；试点期每周看一次数据 |
| 审计日志漏关键操作 | Phase 2 LLM 调用不可追责 | Phase 1 验收时逐操作核对审计记录 |
| LLM 成本与密钥泄露 | 费用失控 / 安全事故 | 密钥走环境变量；调用量进审计并设月度预算告警 |
| LLM 输出不稳定 | 建议质量波动 | 只产建议不产结论；输出带原文引用便于人核 |

## 变更纪律

每期范围锁死，中途新增一律记入下一期；Phase 2 的任何需求若触碰「LLM 参与结论」一律拒绝并记录。
