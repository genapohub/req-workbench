## 1. 产品定位

面向公司内部员工、产品经理和技术评估人，把员工的模糊诉求还原成有业务上下文、有证据、有判断依据的需求卡。

一句话定位：**先补齐业务基座，再挖真实场景，最后辨别需求真假。**

核心约束：**系统只能给判断依据，不能替人拍板**。运行时不调用任何大模型，「智能分析」是确定性规则引擎（`backend/app/analysis.py`），同一份输入永远同一份输出；证据不足时强制保持「待验证」，出现反证时优先降级，低频高影响需求不自动拒绝。

## 2. 核心目标

| 目标 | 说明 |
|---|---|
| 还原真实问题 | 不把用户说的方案直接当需求 |
| 建立判断基座 | 公司业务、项目背景、项目进度必须可编辑、可引用 |
| 区分事实和推断 | 用户陈述、证据、反证、规则推断分开展示 |
| 支撑人工评审 | 输出可评审、可追溯的需求卡草案 |

## 3. 用户角色

| 角色 | 账号 | 主要操作 | 可见菜单（实测） |
|---|---|---|---|
| 管理员 | admin | 全部功能 + 账号管理 | 工作概览、需求挖掘、基座信息、账号管理 |
| 需求负责人（PM） | product | 维护基座、补证据、运行分析、评审判断、导出需求卡、账号管理 | 工作概览、需求挖掘、基座信息、账号管理 |
| 普通员工 | employee | 提交原话、补充追问、查看自己的需求 | 工作概览、需求挖掘、基座信息 |
| 技术评估人 | engineer | 查看需求，补充技术风险和成本建议 | 工作概览、需求挖掘、基座信息 |

演示账号初始密码由环境变量 `WORKBENCH_INIT_PASSWORD` 注入（未注入则随机生成并在服务端日志打印一次），初始账号首次登录强制改密。权限模型：4 角色 / 11 权限位 RBAC，接口级服务端强制鉴权；员工仅见本人提交的需求。实测权限（隔离临时库 + TestClient）：admin 为全部 11 权限位（含 audit.view/users.*），product 为 10 权限位（无 audit.view），employee 与 engineer 各 4 权限位。

## 4. 功能范围（已实现）

### 4.1 工作概览（`/overview`）

指标卡：项目数、基座完整项目、待验证需求、已佐证需求；下方为评审状态、问题真实性、投入优先级分布（数字 + 占比条）。存在基座不完整项目时顶部显示 warning 提示。

### 4.2 基座信息（`/projects`）

每个项目维护：

| 字段 | 要求 | 用途 |
|---|---|---|
| 公司业务 | 核心字段 | 判断需求是否贴合公司业务链路 |
| 项目背景 | 核心字段 | 判断当前阶段、目标用户和项目边界 |
| 项目进度 | 核心字段 | 判断当前是否适合投入 |
| 业务目标 | 建议填写 | 关联需求价值 |
| 关键流程 | 建议填写 | 定位卡点环节 |
| 目标用户 | 建议填写 | 定位服务对象 |
| 约束条件 | 建议填写 | 辅助判断风险和成本 |

三个核心字段缺失时项目可保存（黄色标签提示缺项），但需求提交和智能分析会被拦截并提示先补齐。

**项目提需入口**：每个项目生成公开链接 + 二维码（复制链接 / 查看二维码），员工微信扫码或浏览器打开 `/submit/{projectId}` 免登录提交，表单回显项目名称，字段：标题、用户原话（必填）、最近一次真实场景、当前卡点、影响说明、姓名、部门（可选）。提交后进入需求池草稿状态，由 PM 继续补证据、追问和评审。

### 4.3 需求挖掘（`/requirements`）

员工提交：所属项目、标题、用户原话、发生场景、真实问题、影响说明。

**三视图**（默认看板）：

| 视图 | 形态 |
|---|---|
| 看板 | 按状态分列的卡片墙（草稿 / 澄清中 / 待评审 / 已入池 / 暂缓 / 不采纳，列头带计数） |
| 需求池 | 表格，按优先级排序（高→中→低→待评估，同级按挖掘深度降序） |
| 列表 | 全量表格，支持关键词搜索 + 项目/真实性/优先级/状态筛选 + 列显隐 + 密度切换 |

状态变更属「评审判断」，须与真实性、优先级一起在抽屉里由人确认，**不做看板拖拽改状态**。

需求详情抽屉（`/requirements?req={id}`，宽 560px）分区顺序：使用流程引导 → 判断总览 → 基座引用 → 基座背书 → 真实场景还原 → 证据与疑点 → 方法论检查 → 深挖建议 → 评审判断 → 时间线；底栏固定「关闭 + 导出需求卡」。操作入口：编辑需求（标题/原话/场景/问题/影响）、补充证据（支撑或反证）、补充追问。

### 4.4 需求辨伪

| 维度 | 取值 | 规则 |
|---|---|---|
| 问题真实性 | 待验证 / 已佐证 / 存在反证 | 由证据和反证决定 |
| 业务相关性 | 待明确 / 直接相关 / 间接相关 | 基于基座信息判断；基座未命中时用同项目已入池需求历史文本兜底 |
| 投入优先级 | 待评估 / 高 / 中 / 低 | 基于四维评分和证据充分度 |
| 挖掘深度 | 0–5 | 场景、问题、影响、证据、方案完整度 |

**方法论检查**（四张卡，规则引擎输出，不展示为事实结论）：JTBD 场景、5 Whys、证据链、RICE 四维；未满足时分别提示缺真实场景 / 继续追问 / 保持待验证 / 不生成综合优先级。卡片带白话注释，抽屉顶部有「挖掘 → 分析 → 辨伪」使用流程引导。

**基座背书**：同项目已入池需求按业务词重合度（中文 2-gram + 英文按词）取 Top3 为新需求背书，展示重合词与疑似同类标记；背书只在详情与分析接口计算，不落库。

### 4.5 导出需求卡

导出 Markdown 需求卡草案：基座信息、用户原话、真实问题、判断结论、证据、候选方案、深挖建议、评审记录；未确认内容保留待补充标记。

### 4.6 账号管理（`/users`）

账号新增、编辑、删除、启停、部门字段、角色选择；禁止删除当前登录账号；不传密码则随机生成初始密码（创建成功后仅展示一次），新建与被重置密码的账号首次登录强制改密；所有登录用户可在用户菜单自助修改密码。角色、菜单、权限为内置预留模型，不做完整权限配置后台。

## 5. 页面清单（与代码一致，6 视图）

| # | 页面 | 路由 | 核心用途 |
|---|---|---|---|
| 1 | 登录 | `/login` | 账号登录 |
| 2 | 工作概览 | `/overview` | 基座完整度和需求判断分布 |
| 3 | 基座信息 | `/projects` | 项目基座维护 + 提需入口（复制链接 / 二维码） |
| 4 | 需求挖掘 | `/requirements` | 看板/需求池/列表三视图，提交原话，进入详情 |
| 5 | 需求详情抽屉 | `/requirements?req={id}` | 追问、证据、分析、辨伪、导出 |
| 6 | 账号管理 | `/users` | 账号增删改查、启停、角色、部门 |
| 7 | 公开提需表单 | `/submit/:projectId` | 员工免登录提交需求原话（公开页，不进导航） |

导航（按角色下发）：工作概览、需求挖掘、基座信息、账号管理（仅管理员）。

## 6. 主流程

```text
维护基座信息 → 提交用户原话（后台或公开表单）→ 补充追问和证据
→ 运行方法论检查与智能分析 → 人工确认真实性、相关性、优先级
→ 状态流转（草稿/澄清中/待评审/已入池/暂缓/不采纳）→ 导出需求卡草案
```

## 8. 产品红线

- 系统只给判断依据，不替人拍板；运行时不调用大模型。
- 证据不足保持待验证；待验证/待明确用中性色，不制造已确认感。
- 基座缺失必须醒目提示，并拦截需求提交与智能分析。
- 状态变更须由人确认，不做拖拽改状态。
