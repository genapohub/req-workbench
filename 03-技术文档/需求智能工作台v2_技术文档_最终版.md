## 1. 架构选型

单体轻量架构，服务于基座信息、需求挖掘和需求辨伪。

| 层 | 选型 |
|---|---|
| Web 前端 | Vue 3 + Vite + Element Plus（无 Pinia、无 TypeScript、无 SCSS） |
| 后端 API | FastAPI（fastapi 0.141.1 / pydantic 2.13.5 / uvicorn 0.54.0 / httpx / python-multipart） |
| 本地数据库 | 原生 SQLite（无 ORM），每表 `(id TEXT PRIMARY KEY, body TEXT)`，业务对象 JSON 存储 |
| 登录会话 | HttpOnly Cookie `workbench_session`，scrypt 加盐哈希，token 强随机 7 天过期 |
| 前端 Mock | MSW（24 个 mock 接口，镜像后端算法），仅限开发环境；生产构建不含 Mock 与演示数据 |
| 智能分析 | 确定性规则引擎 `app/analysis.py`（393 行），运行时不调用任何大模型 |
| 本地运行 | Python 3.14（`06-项目编码/.venv`），PyCharm 三个运行配置 |

设计取舍：不引入多智能体框架、独立向量库、复杂权限后台；前端不引入 Vitest 与 Pinia，以「后端 pytest + vite build + Playwright 冒烟」兜底。

### 目录与模块

```text
06-项目编码/
├── .venv/          # 项目本地 Python 解释器（3.14）
└── v2/
    ├── backend/    # FastAPI（app/ 17 个 .py，约 1,735 行含测试）
    └── frontend/   # Vue 3（src 约 4,600 行：6 视图 + 12 公共组件 + 24 个 MSW mock，仅开发环境）
```

后端 router 模块：`auth`（登录/退出/当前用户）、`overview`（工作概览）、`projects`（基座信息）、`requirements`（需求 CRUD/追问/证据/分析/深挖/评审/导出）、`public`（公开提需表单）、`users`（账号管理）；`analysis.py` 为规则引擎，`deps.py` 认证与 RBAC，`resp.py` 统一响应。

### 前端样式架构

- 单一事实源 `frontend/src/styles/tokens.css`（Design Tokens v3.0，Spotify 式深色），EP 覆盖层 `overrides.css`；只改 Token 取值即可整体换肤，浅色骨架保留在 `[data-theme="light"]`。
- 11 个公共组件：AppSidebar / AppTopbar / PageHeader / PanelCard / DataTable / FormDialog / StatCard / EmptyState / SectionTitle / MethodCheckCard / StatusTag。

## 2. API 接口契约

完整机器可读契约见本目录 `openapi.yaml`（19 paths / 24 操作）。基本约定：

| 项 | 约定 |
|---|---|
| Base URL | `http://127.0.0.1:8012/api` |
| 鉴权 | HttpOnly Cookie `workbench_session` |
| 统一响应 | `{ "code": 0, "data": {...}, "message": "ok" }` |
| 错误响应 | `{ "code": <业务码>, "data": null, "message": "中文可读" }` |

错误码：`0` 成功；`1001` 未登录/会话过期（401）；`1002` 账号或密码错误（401；登录同一账号连续失败 5 次锁定 10 分钟，锁定期返回 429）；`1003` 无权限（403）；`2001` 资源不存在（404）；`2002` 唯一性冲突（409）；`3001` 参数校验失败/基座缺失（422）。

### 接口清单（24 个）

| 模块 | 接口 | 权限 |
|---|---|---|
| 健康检查 | GET /healthz | 公开 |
| 鉴权 | POST /auth/login、POST /auth/logout、GET /auth/me、POST /auth/change-password | 登录 |
| 工作概览 | GET /dashboard | overview.view |
| 基座信息 | GET /projects、POST /projects、PUT /projects/{id} | projects.view / projects.manage |
| 需求挖掘 | GET /requirements、POST /requirements、GET /requirements/{id}、PATCH /requirements/{id} | requirements.view / create / review（PATCH 支持标题/原话/场景/问题/影响/判断结论） |
| 辅助操作 | POST /requirements/{id}/clarifications、/evidence、/analyze、/deep-dive | requirements.analyze 或本人补充 |
| 导出 | GET /requirements/{id}/export.md | requirements.export |
| 公开提需 | GET /public/projects/{project_id}/form、POST /public/projects/{project_id}/requirements | 无需登录（基座不完整返回 3001） |
| 账号管理 | GET /users、POST /users、PUT /users/{user_id}、DELETE /users/{user_id} | users.view / users.manage（禁止删除当前登录账号） |

### 关键字段

基座字段：`company_business`、`project_background`、`progress`（三个核心字段均非空时 `base_complete=true`）、`business_goals`、`business_process`、`target_users`、`constraints`。

判断字段：`authenticity`（pending/supported/contradicted）、`business_relevance`（unknown/direct/indirect，分析时可带 `business_relevance_endorsed_by` 背书来源，不落库）、`priority`（unassessed/high/medium/low）、`depth`（0–5）、`status`（draft/clarifying/review/pooled/deferred/rejected，6 态状态机）。

需求详情返回 `method_cards`（name/status/text，status 取 `ok`/`missing`），当前内置 JTBD 场景、5 Whys、证据链、RICE 四维四项；`base_endorsements` 返回同项目已入池需求背书（shared_terms / overlap / overlap_level，high≥3）。

## 3. 数据库设计

原生 SQLite（`backend/运行数据/工作台.sqlite3`），业务对象以 JSON body 存储，无 ORM、无外键、无迁移框架（一期试点取舍）。5 张表：

| 表 | 内容 |
|---|---|
| users | id、username、name、role_ids、department_id、status、password（scrypt 哈希） |
| roles | id、name、permissions |
| projects | id、name + 基座字段（见 §2）、created_at/updated_at |
| requirements | id、project_id、proposer_id、title、original、scenario、problem、impact、四维判断字段、depth、四维评分、clarifications、evidence、solutions、analysis_history、deep_dive_suggestions、status、时间戳 |
| sessions | id、user_id、expires |

权限位（10 个，定义于 `app/config.py`）：`overview.view`、`projects.view`、`projects.manage`、`requirements.view`、`requirements.create`、`requirements.analyze`、`requirements.review`、`requirements.export`、`users.view`、`users.manage`。

角色默认授权（`config.py` ROLE_DEFAULTS，启动时对 roles 表做轻量 upsert）：admin=全部 10 项；pm=同样 10 项（含 users.view/users.manage，与 admin 等权）；staff=overview.view、projects.view、requirements.view、requirements.create（4 项）；tech=overview.view、projects.view、requirements.view、requirements.review（4 项）。菜单按权限下发：含 users.view 的角色可见「账号管理」菜单。

## 4. 本地运行与联调

PyCharm 三个运行配置（两前端配置共用 5173，同一时间只能启动一个）：

| 配置 | 用途 | 依赖 |
|---|---|---|
| 后端 FastAPI v2 8012 | 真实后端 API | — |
| Web 前端 v2 5173 Mock验收 | `VITE_USE_MOCK=true`，不依赖后端 | 无 |
| Web 前端 v2 5173 API联调 | `VITE_USE_MOCK=false VITE_API_TARGET=http://127.0.0.1:8012` | 后端 8012 |

兜底命令：

```bash
# 后端
cd 06-项目编码/v2/backend
../../.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8012 --reload
# 验证 http://127.0.0.1:8012/api/healthz

# 前端（Mock 验收 / API 联调二选一）
cd 06-项目编码/v2/frontend
VITE_USE_MOCK=true npm run dev
VITE_USE_MOCK=false VITE_API_TARGET=http://127.0.0.1:8012 npm run dev
```

验证命令：


## 5. 生产级验收结论（2026-10-01）

**当前不满足生产级标准，不建议直接投产。** 定位为功能完整、安全基础合格的 MVP 试点版本。

| 维度 | 评级 |
|---|---|
| 功能完整性 | ✅ 达标（主链路闭环，23 项测试全过，2026-10-27 复跑） |
| 认证与会话 | ✅ 达标（2026-10-27 修复：初始密码环境变量注入或随机生成、自助改密 + 改后失效其它会话、登录防爆破、首登强制改密） |
| 权限与数据隔离 | ✅ 达标（服务端强制 RBAC，员工仅见本人需求） |
| 注入/XSS 防护 | ✅ 达标（SQL 全参数化，无 v-html） |
| 生产部署形态 | 🚫 不达标（开发模式运行，无守护/反代/HTTPS） |
| 数据存储 | ⚠️ SQLite JSON-blob，有容量天花板（≤50 用户/数百条需求可用） |
| 审计与可观测 | 🚫 无审计日志、无监控告警 |
| 构建产物安全 | ✅ 达标（2026-10-27 修复：Mock 仅限开发环境动态导入，生产构建产物不含 MSW 与演示数据；`mockServiceWorker.js` 为 MSW 通用 worker，不含任何业务数据与凭证） |

整改清单：

- **P0（已全部修复，2026-10-27）**：① 初始口令改为环境变量 `WORKBENCH_INIT_PASSWORD` 注入，未注入时随机生成并仅在服务端日志打印一次；② Mock 改 `import.meta.env.DEV` 门控的动态导入，生产 bundle 零 Mock 零演示凭证；③ 新增 `POST /api/auth/change-password`（校验原密码 + 强度 + 改后失效其它会话），前端用户菜单加「修改密码」入口，初始/被重置账号首登强制改密；④ 登录同一账号连续失败 5 次锁定 10 分钟（内存计数），失败事件记日志。
- **P1（投产前建议）**：审计日志；生产部署（去 reload、Nginx+HTTPS、systemd、dist 托管）；SQLite 存储升级；公开表单防刷；CORS 收紧；安全响应头；校验错误统一包裹；前端补 Vitest。
- **P2（可排期）**：SQLite 文件入 gitignore；`@app.on_event` 改 lifespan；列表分页与过期会话清理；备份策略；依赖漏洞审计；localStorage token 双通道收敛；mock 种子与后端种子漂移（前端 24 条 vs 后端 1 条）。

投产路径：~~修 P0~~（已完成）→ P1-1 审计日志 + P1-2 生产部署（2–3 人日）→ 其余 P1+P2（1–2 人日）→ 单团队试点（≤50 人，2–4 周）→ 规模化前存储升级。
