## 一、结论摘要

| # | 问题 | 结论 | 证据强度 |
|---|---|---|---|
| 1 | 能否在 req-workbench 上迭代这批功能 | **不能迭代，只能「借壳重建」**。两产品领域零重叠：现有代码只服务「需求真伪分析」，CRM 的 13 个模块里没有一条业务链路可以增量改造而来 | 【实测】+【推断】 |
| 2 | 能否复制一份项目重新命名 | **可以**。推荐「白名单复制」而不是整仓 `cp`：只搬前端壳层与通用组件（约 2,052 行），后端几乎不搬；排除 `.git`、`node_modules`、`dist`、`.venv`、运行数据 | 【实测】 |
| 3 | 开发语言能否用 PHP | **完全可行**，前端与后端语言无关。但**推荐 Django 而非 PHP**（方案 A）；若交付环境明确要求 PHP，直接换 Laravel（方案 B），前端资产一行不改 | 【实测】+【文档口径】 |
| 4 | 建议动作 | 新建独立仓库 `crm-service`；技术栈 **Python 3.12 + Django 5 + DRF + MySQL + 复用现成 Vue3 壳**；一期只做 M1/M2/M3/M13，先补产品规格再编码 | 建议 |

**一句话判断**：这不是「给现有系统加模块」，而是「用现有项目的 UI 骨架和工程习惯，另起一个 CRM 产品」。共享的是骨架，不是业务。

### 2.1 需求清单本身

清单结构完整、业务描述清楚，但**不具备直接进入编码的条件**。

| 模块 | 核心能力 | 关键外部依赖 | 复杂度档位 |

**缺口（会直接卡住编码）**：

1. **无优先级**：13 个模块平铺，没有 MVP 边界。
2. **无验收标准**：每条都是功能点描述，没有「做到什么算完成」的判据。
3. **无数据模型**：客户/合同/任务/需求/工单/报价之间是多对多还是主子表、状态机有哪些非法跃迁，全部未定义。
4. **无权限矩阵**：只有「按模块+数据范围」一句话，数据范围（本人/部门/全部）、代理商与终端客户的价格可见性隔离都要重新设计。
5. **无迁移口径**：现有客户资料、实施计划、合同大概率在 Excel 里，字段映射与历史数据导入策略未给。
6. **无提醒渠道的技术前提**：企业微信需要企业主体与自建应用、短信需要签名与模板报备、支付需要商户号——这些是资质前置，不是代码问题。
7. **版本号自相矛盾**：文件名 `V1.0(1)`，正文标题 `V2.0`，且带 `(1)` 说明是重复下载件。进入开发前必须定版。

> 结论：**规格先行**。编码前需补一份《产品规格 v1.1》＋《数据模型与状态机》，把上表 7 项缺口补齐；否则任何一个模块都会在开发中反复返工。

**存储模型是最大障碍**【实测】：

- 只有 5 张表，全部是 `(id TEXT PRIMARY KEY, body TEXT)`，整条记录 `json.dumps` 后塞进 `body`（`backend/app/database.py:28-45`）。
- 无外键、无索引、无唯一约束、无 Alembic 迁移，启动时仅 `CREATE TABLE IF NOT EXISTS`（`backend/app/database.py:25-28`）。
- CRM 需要按合同到期日、任务逾期、负责人、数据范围做大量条件查询与统计——JSON 单列存储无法支撑。**这不是改造能解决的，是换存储模型。**

**能力缺口**【实测】：无多租户、无审计日志、无文件上传、无通知、无定时任务、无分页（列表全量返回）、无正规报表（仅 `routers/overview.py:23-38` 的内存聚合）。

**测试**：2 个文件 17 个用例，实测全过【文档口径，本轮未复跑】。用例本身在固化「范围已收窄」，例如 `backend/tests/test_v2.py:144-159` 断言旧接口必须 404。这印证了产品方向已经收敛为需求分析工具，与 CRM 无关。

## 四、技术方案对比

### 4.1 三方案

| 维度 | **A（推荐）Python + Django** | B PHP + Laravel | C 沿用 FastAPI |
|---|---|---|---|
| 栈 | Python 3.12 + Django 5 + DRF + MySQL + Vue3 壳 | PHP 8.3+ + Laravel 12 + MySQL + Vue3 壳 | FastAPI + SQLAlchemy + Alembic + Vue3 壳 |
| 与本项目复用 | 前端壳 ~40% | 前端壳 ~40% | 后端 ~10% + 前端壳 ~40% |
| 起步成本 | 中（需建 Django 工程与 DRF 规范） | 中高（本机零 PHP，需装运行时＋Composer） | 中（无迁移工具，需补 Alembic/分层） |
| 13 模块适配度 | **高**：ORM/迁移/权限/Admin/信号/定时任务开箱即用 | **高**：迁移/队列/调度/通知/Excel 生态同档 | **中**：权限、后台、报表、队列、审计都要自建 |
| 后台管理 | Django Admin 直接承载客户/合同/字典/SLA/积分规则 | 需另做（Filament 或自建） | 需另做 |
| 长期维护成本 | 低 | 低 | **最高**（框架能力缺口会被 13 模块放大） |
| 主要风险 | 脱离团队现有 FastAPI 习惯 | 陌生语言栈；PHP 未验证 | 技术债在二期集中爆发 |

### 4.2 为什么推荐 A

1. **存量语言是 Python**：本项目 3 年后端积累都在 Python，团队认知与调试链路可直接迁移；PHP 是全新语言栈。
2. **Django Admin 省掉一整个后台**：M13 的组织/账号/角色/参数配置、M5 价目库、M10 SLA 规则、M7 积分规则，都能先用 Admin 承载运营配置，前端只做业务页面。
3. **迁移与建模是 CRM 的生死线**：60~80 张表会持续演进，Django migrations 与 ORM 关系建模比现有 JSON 单表方案强一个量级。
4. **DRF 输出标准 REST**，现有 Vue3 壳与 axios 拦截器可直接对接，前端无需改动架构。
5. **PHP 随时可换**：方案 A 与 B 的差异只在服务端，前端 2,052 行复用资产完全一致——先按 A 起步不会锁死 PHP 路线。

### 4.3 PHP 可行性专章

**结论：可行，不是障碍。**

| 判断点 | 事实 | 强度 |
|---|---|---|
| PHP 能否实现这 13 个模块 | 能。Laravel 12 自带迁移、队列、任务调度、通知（邮件/短信/企微 webhook）、Excel、PDF、权限包 | 【文档口径】 |
| 前端是否受影响 | 不受影响。Vue3 通过 HTTP 调后端，语言无关 | 【实测】架构判断 |
| 本机能否立刻开工 | **不能**：PHP/Composer/MySQL 客户端均未安装；brew 可装 PHP 8.5.11，Composer 需另装 | 【实测】 |
| Laravel 12 与 PHP 8.5 的兼容性 | **未验证**（本轮没有安装 PHP，未实际起过 Laravel） | 未验证 |
| 真实约束 | 不是语言能力，而是**团队是否愿意长期维护 PHP**；以及交付/运维环境是否已标准化 PHP | 待拍板 |

> 若选 B：接口约定、数据模型、前端页面完全不变，只把 Django 层替换为 Laravel；`rsync` 白名单复制方案同样适用。

### 4.4 为什么不推荐 C（沿用 FastAPI）

现有后端不是「一个待扩展的框架」，而是「一个已收敛的单产品」。选 C 意味着：SQLAlchemy 分层、Alembic 迁移、RBAC 数据范围、审计、通知、定时任务、报表、后台管理**全部自建**，且要背着我方 393 行需求分析逻辑与 5 张 JSON 表的历史包袱。13 个模块下，这些缺口会在二期集中爆发。
