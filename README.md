# 需求智能工作台 v2

> 一个**内部需求辨伪与挖掘工具**：解决的不是「需求怎么管理」，而是「员工提上来的是不是真需求」。

## 这是什么

员工提需求时往往直接给**解决方案**（「我要一个导出按钮」），而 PM 缺少业务上下文，无法判断真伪。本工作台把判断过程产品化：

```
业务基座 → 场景还原 → 证据 / 反证 → 方法论检查 → 人工拍板
```

核心约束：**系统只能给判断依据，不能替人拍板**；证据不足时强制进入「待验证」，出现反证时优先降级，低频高影响需求不自动拒绝。

## 这不是什么（重要）

**本项目运行时不调用任何大模型。** 所谓「智能分析」是一套**确定性规则引擎**（`06-项目编码/v2/backend/app/analysis.py`），依赖中没有任何 LLM SDK。

这不是缺陷，是刻意的设计选择：

| 诉求 | 做法 |
|---|---|
| 需求判断必须可复现、可追责 | 用规则而非模型，同一份输入永远同一份输出 |
| 不许编造业务背景 | 基座信息缺失时直接限制分析，而不是让模型「猜」 |
| 反幻觉 | 把「不得编造」写成可测试的代码约束，而不是靠 prompt 祈祷 |

AI 用在了**开发流程与人机边界设计**上（让 AI 按契约写代码、人工兜底），而不是运行时。

## 技术栈

| 层 | 选型 |
|---|---|
| 后端 | FastAPI + 原生 SQLite（业务对象以 JSON body 存储，未使用 ORM） |
| 前端 | Vue 3 + Vite + Element Plus |
| 前端 Mock | MSW（Mock Service Worker），镜像后端算法，演示环境可脱离后端运行 |
| 测试 | pytest（后端 23 项） |

规模：**24 个接口 / 5 张表 / 约 6900 行代码**。

## 当前功能

| 模块 | 作用 |
|---|---|
| 工作概览 | 项目数量、基座完整度、待验证需求、已佐证需求 |
| 基座信息 | 公司业务、项目背景、项目进度、业务目标、关键流程、约束 |
| 需求挖掘 | 提交用户原话，还原场景 / 问题 / 影响，补充追问与证据 |
| 需求辨伪 | 判断问题真实性、业务相关性、投入优先级、挖掘深度（含 JTBD / 5 Whys / 证据链 / RICE 方法论检查） |
| 需求卡导出 | 导出 Markdown 需求卡草案，未确认内容保留待补充标记 |
| 项目提需入口 | 每项目生成公开链接 + 二维码，员工扫码即可提需 |
| 三视图需求管理 | 看板（按状态分列）/ 需求池（按优先级排序）/ 列表三种视图 |
| 基座背书 | 同项目已入池需求按业务词重合度为新需求提供背书与相关性兜底 |
| 账号管理 | 4 角色 / 10 权限 RBAC，6 态需求状态机 |

## 本地启动

```bash
# 后端
cd 06-项目编码/v2/backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8012 --reload
# 验证：http://127.0.0.1:8012/api/healthz

# 前端（另开终端）
cd 06-项目编码/v2/frontend
npm install
npm run dev
# 打开 http://127.0.0.1:5173
```

前端两种验收模式：**Mock 验收**（脱离后端跑通 UI）与 **API 联调**（打真实后端），通过环境变量切换。

## 使用流程

1. 「基座信息」补齐公司业务、项目背景、项目进度（缺失会限制分析与提需）
2. 「需求挖掘」提交员工原话与发生场景
3. 需求详情里补充追问、证据或反证
4. 点击智能分析 → 得到问题真实性、业务相关性、优先级、挖掘深度
5. 人工确认结论：已入池 / 暂缓 / 不采纳
6. 导出需求卡草案，交下游研发流程
